
> UI라는건 기본적으로 '내부 데이터'를 보여주는 개념이다.

라고 한다면, 많은 사람이 동의하지 않을 것이다.
왜냐하면 이것만으로는 UI를 정의할 수 없으니까. UI는 보여주는 것으로 끝나는게 아니라 유저와 상호작용하는 도구이기도 하니까.

UX에 대한 부분을 제외한다면, (즉 디자인과 관련한 부분을 제외한다면)
UI는 본질적으로 '데이터 View'와 '유저 상호작용' 두개의 책임을 가지는 개념이다.

그런데, '보여주는 작업'과 '상호작용하는 작업'을 하나의 클래스에서 처리하려니까 뭔가 책임소재도 모호해지고 관리도 어렵다는 느낌을 받았다.

그래서, UI는 View UI 클래스와 Interact UI 클래스로 구분했다.
Unity에서는 '컴포넌트'가 되겠다.

MVP패턴과 미리 비교하자면, 델리게이트(이벤트, 콜백, 무슨 이름이든...)를 사용해서 'view update behavior'를 passive view에 interface로 집어넣은 구조이다.
MVP에서는 'view update behavior'를 `controller`에게 위임하는 것과 차이가 있다.


## ViewUI

View만 기능하는 UI이다.
외부는 아예 모른다. 
Initialize 시점에 ViewInterface를 주입받는다.
해당 인터페이스는 '초기 데이터'와 '갱신 이벤트'를 제공한다.
해당 이벤트 콜백에 View 갱신 함수를 등록해서 동작한다.

## InteractUI
(전제: input을 직접적으로 receive받는 객체. 또는 receive 할 수 있는 객체)
InteractUI만 기능하는 UI이다.
외부는 아예 모른다. 입력을 어떻게 처리해야 할지 모른다. 예를 들어 특정 상황에서는 입력을 막는다던가, 입력을 지연시켜서 처리해야 한다던가... 그런거 모른다.
Initialize 시점에 InteractInterface를 주입받는다.
해당 인터페이스는 대상 UI가 receive하는 interact input에 대응하는 메서드를 제공한다.
UI는 receive한 input에 대해 'interface객체가 제공하는 함수'를 적절하게 call하는 방식으로 외부 입력을 전달 및 처리한다. 입력 처리 policy의 경우 인터페이스 구현체의 책임으로 본다.

## 이런 사고의 계기
팀 프로젝트 하면서 'UI 맡아주세요' 하고 맡겼는데 몇가지 이슈가 있었다.
1. '원본 데이터가 없어서 작업하기 어렵다'라는 것
2. 원본 데이터 역할을 하는 더미 객체를 만들고 그 더미 객체에 대응하는 UI를 만들었는데  그게 실제 객체 형태랑 달라서 UI 코드랑 시스템 코드랑 합치기 어려웠다는 점.
그래서 '이런 형태로 데이터가 있을거고 갱신 이벤트도 여기 있을거에요~'하고 미리 약속을 인터페이스로 하면 이런 문제를 해결할 수 있겠다고 생각했다.

또한 ui를 만드는데 Unity UI Object에서 `Button`을 남발하는 등 interact하는 부분과 view하는 부분이 섞여서 팀원의 코드를 제대로 알아보고 책임을 분리하기 힘들었던 경험에서 나왔다.

## 시간이 지나고 review
당시엔 꽤 괜찮은 패턴이라 생각했는데, 지금 와서 보니까 문제가 좀 있다.
특히 interact쪽이 허술하다.
외부 input이라는건 애초에 receive할 때 receive하는 쪽에서 전처리가 필요한 경우가 있는데, 'Dumb Interact UI'를 유지한다는 규칙을 지키려고 하면 received input preprocess가 있을 공간이 없다는 점이다.


'협업하기 위해 interface를 사용한다'라는 부분이랑
'UI는 View랑 Interact로 구분한다'라는 부분은 충분히 좋은 개념이고 계속 가져가도 될 것 같은데

ViewUI - ViewInterface 구조랑
Interact - InteractInterface 구조를 그대로 가져가도 될지는 모르겠다.

ViewUI - ViewInteface 구조는 충분히 마음에 들고 자주 사용하게 되는데
Interact부분이 모호하고 실제로 사용하기에 어려운 경험이 있었다.
