> UI란 무엇인가?

UI를 뭐라고 정의할 수 있을까? 생각해봤다.

'내부 정보를 보여주는 것'이라고 하면, 적절할까?
체력바는 현재 체력을 보여주고, 인벤토리는 아이템 데이터를 보여주고, 버튼 옆의 텍스트는 지금 가능한 행동을 보여준다.

그런데 UI를 `View`라고만 말하면 뭔가 빠진다.

UI는 보여주는 것에서 끝나지 않는다.
유저는 UI를 통해 버튼을 누르고, 값을 조정하고, 선택지를 고르고, 어떤 행동을 요청한다.
즉 UI는 내부 데이터를 보여주는 장치이면서, 동시에 유저 입력을 시스템에 전달하는 장치이기도 하다.

엄밀하게 말하면 여기에 Design, UX 같은 축도 들어간다.
무엇을 어떤 우선순위로 보여줄지, 어떤 흐름으로 조작하게 할지, 유저가 어떤 감각을 받게 할지도 UI를 말할 때 빼놓을 수 없다.
다만 코드 구조를 고민하는 입장에서, 디자인을 잠시 빼고 이야기하자면

> UI는 본질적으로 View + Interact

이정도면 충분히 UI를 정의한 것이라고 본다.

```text
View
- 내부 데이터를 유저가 볼 수 있는 형태로 보여준다.

Interact
- 유저 입력을 받아서 시스템에 영향을 전달한다.
```

UI를 View와 Interact로 나눠서 보면 서로 다른 책임이 한 클래스 안에서 섞이고 있었다는 게 보인다.

이 표현이 그냥 당연한 말처럼 보일 수도 있다.
그런데 실제로 Unity에서 UI를 만들다 보니까, 이 두 책임이 한 클래스 안에 같이 들어갈 때 코드의 역할과 책임이 모호해지는 경향이 있었다(적어도 내 경험에서는 그랬다).

Text를 갱신하는 코드가 있고,
Image를 바꾸는 코드가 있고,
Button의 onClick을 등록하는 코드가 있고,
그 onClick 안에서 실제 게임 시스템 값을 바꾸는 코드가 있고,
또 특정 상황에서는 버튼을 막아야 해서 조건문이 들어가고,
그 조건문을 위해 다른 시스템 참조가 들어온다.

이런 식으로 조금씩 쌓이다 보면 UI 클래스가 "화면을 그리는 객체"인지, "입력을 처리하는 객체"인지, "도메인 로직을 일부 알고 있는 객체"인지 애매해진다.

## 계기

이 생각이 처음 나온 건 팀 프로젝트에서 UI 작업을 나누면서였다.

"UI 맡아주세요" 하고 팀원에게 맡겼는데, 몇 가지 문제가 발생했었다.

첫 번째는 원본 데이터가 없으면 UI 작업을 진행하기 어렵다는 점이었다.
(난 UI는 원본 코드 없이도 완수할 수 있는 작업이라 생각하는데, 그 팀원에겐 그렇지 않았나보다.)

예를 들어 UI는 체력, 점수, 상태, 선택된 아이템 같은 데이터를 보여줘야 하는데, 그 데이터가 실제로 어떤 객체에서 어떤 형태로 나올지 아직 안정되어 있지 않았다.

그래서 나는 '더미 데이터를 만들어서 쓰세요.'라고 했다.

두 번째 문제는 그 더미 데이터가 나중에 실제 시스템 객체와 맞지 않을 수 있다는 점이었다.

UI 작업할 때는 이런 형태일 거라고 생각해서 더미 객체를 만들었는데, 실제 시스템 코드에서는 전혀 다른 형태로 데이터가 나오면 나중에 합치는 과정이 힘들어진다.
(UI 담당자가 시스템 코드를 참조해서 자기 UI코드를 고치는게 옳다고 생각하지만, 그 때 그거 합치는걸 내가 하겠다고 해서 양쪽 코드를 모두 보면서 처리하는게 좀 힘들었다.)

이때 내가 생각한 건 이런 거였다.

```text
"실제 구현체가 아직 없어도,
UI가 필요로 하는 데이터의 형태와 갱신 이벤트만 먼저 약속할 수 있지 않을까?"
```

즉 UI가 실제 시스템 객체를 직접 아는 대신,
"이런 데이터가 있을 거고, 이 데이터가 바뀌면 이런 이벤트가 올 거다"라는 약속만 보고 작업하게 만드는 것이다.

이 생각이 ViewUI 쪽으로 이어졌다.
그래서 `ViewUI + ViewInterface` 라는 형태로 UI를 정의할 수 있다고 느꼈고, 내 생각을 정리해보았다.

그런데 UI라는건 막상 `View`의 책임만 갖고 있는게 아니었고, `Interact`의 책임도 가지고 있었다. 그래서 `ViewUI`에서 채택한 Interface 주입의 방식을 `Interact`에도 그대로 적용해서 UI를 두개의 개념으로 나누고, 각각의 개념을 다루는 방식에 interface 주입이라는 방식을 채택했다.

## ViewUI

`ViewUI`는 말 그대로 View만 담당하는 UI이다.

`ViewUI`는 외부 시스템을 모른다.
플레이어가 누구인지, 인벤토리가 어떤 구조인지, 전투 시스템이 어떤 식으로 돌아가는지 모른다.

대신 Initialize 시점에 `ViewInterface`를 주입받는다.

이 `ViewInterface`는 이런 약속을 제공한다.

```text
1. 초기 표시 데이터
2. 데이터가 바뀌었을 때 발생하는 갱신 이벤트
```

ViewUI는 초기 데이터를 받아서 Text, Image, Slider 같은 표시 객체를 갱신한다.
그리고 갱신 이벤트를 구독해서, 데이터가 바뀔 때마다 다시 표시 객체를 갱신한다.

중요한 건 ViewUI가 직접 데이터를 가져오러 다니지 않는다는 점이다.

ViewUI는 "내가 무엇을 보여줘야 하는지"만 알고,
"그 데이터가 어디서 왔는지"는 모른다.

이 구조는 꽤 마음에 들었다.

특히 협업할 때 좋았다.
실제 시스템 구현이 아직 완성되지 않아도, UI가 필요로 하는 데이터 형태와 이벤트만 인터페이스로 먼저 정해두면 UI 작업을 진행할 수 있다.

나중에 실제 시스템 객체가 완성되면, 그 객체가 `ViewInterface`를 구현하면 된다.

이렇게 하면 UI 입장에서는 더미 객체든 실제 객체든 크게 다르지 않다.
어차피 UI는 약속된 초기 데이터와 갱신 이벤트만 보기 때문이다.

## InteractUI

InteractUI는 유저 입력을 받는 UI이다.

예를 들어 버튼 클릭, 토글 변경, 슬라이더 입력, 드래그 같은 것들이 여기에 해당한다.

처음 생각은 ViewUI와 비슷했다.

InteractUI도 외부 시스템을 직접 알지 않게 만들고 싶었다.
그래서 Initialize 시점에 `InteractInterface`를 주입받고, 입력이 들어오면 그 인터페이스의 메서드를 호출하는 식으로 생각했다.

```text
Button.onClick
→ InteractUI가 입력을 받음
→ InteractInterface.RequestSomething() 호출
```

이러면 InteractUI는 외부 시스템을 모른다.
그냥 "이 입력이 들어오면 이 메서드를 호출한다" 정도만 안다.

입력을 실제로 처리할지,
막을지,
지연시킬지,
실패 사유를 만들지,
사운드를 낼지,
다른 상태를 갱신할지는 InteractInterface 구현체의 책임으로 넘긴다.

처음에는 이것도 괜찮아 보였다.

ViewUI가 데이터를 직접 알지 않고 ViewInterface만 바라보는 것처럼,
InteractUI도 시스템을 직접 알지 않고 InteractInterface만 바라보면 된다고 생각했다.

## 지금 다시 보면

그런데 시간이 지나고 보니까, ViewUI 쪽과 InteractUI 쪽이 완전히 대칭은 아니었다.

ViewUI 쪽은 지금도 꽤 괜찮다고 생각한다.

View는 기본적으로 수동적이다.
데이터가 들어오면 보여주고, 데이터가 바뀌면 다시 보여준다.
물론 복잡한 UI에서는 애니메이션이나 상태 전환이 있을 수 있지만, 그래도 핵심 흐름은 비교적 단순하다.

```text
데이터가 바뀜
→ View 갱신
```

그래서 ViewUI를 dumb하게 유지하는 게 꽤 자연스럽다.

반면 InteractUI는 생각보다 애매했다.

입력은 단순히 전달만 하면 끝나는 게 아닐 때가 많다.
입력을 받는 순간 이미 전처리가 필요할 수 있다.

예를 들어 이런 것들이다.

```text
- 지금 이 입력을 받아도 되는가?
- 더블 클릭으로 봐야 하는가?
- 드래그 중인지 클릭인지 구분해야 하는가?
- 입력을 잠시 버퍼링해야 하는가?
- 입력을 UI 내부 상태와 조합해서 해석해야 하는가?
- 입력 실패를 UI에서 바로 표현해야 하는가?
```

이런 것들은 전부 "입력"과 가까운 문제다.
그런데 InteractUI를 너무 dumb하게 만들면 이 로직을 둘 공간이 애매해진다.

전부 InteractInterface 구현체로 넘기면 UI 입력의 세부 맥락을 구현체가 너무 많이 알아야 한다.
반대로 InteractUI 안에 넣으면 InteractUI가 더 이상 dumb하지 않다.

여기서 내가 처음 만든 구조의 약점이 보였다.

```text
ViewUI - ViewInterface 구조는 꽤 안정적이다.
하지만 InteractUI - InteractInterface 구조는 생각보다 불안정하다.
```

View는 "데이터를 어떻게 보여줄 것인가"의 문제로 비교적 잘 닫힌다.

하지만 Interact는 "입력을 어떻게 해석하고, 어떤 정책으로 처리할 것인가"의 문제가 같이 따라온다.
그래서 단순히 Interface 하나로 빼는 것만으로는 경계가 선명해지지 않았다.

또한, ViewUI가 MVC패턴에서 Controller가 담당하는 'view update behavior' 책임을 Passive View에게 `Interface`라는 방식을 통해 전달한 것과 달리, InteractUI 구조는 실질적으로 input을 그대로 위임하는 것 밖에 되지 않았다.
## 지금 가져갈 생각

그래도 의미 있는 부분이 있다.

```text
1. UI = View + Interact 라는 관점과 해석
2. 협업을 위해 실제 구현체보다 먼저 인터페이스로 약속을 잡는 방식
```

특히 View 쪽은 계속 사용할 만하다.

UI가 실제 시스템 객체를 직접 참조하지 않고,
초기 데이터와 갱신 이벤트만 주입받아서 동작하는 구조는 여전히 마음에 든다.

다만 Interact 쪽은 미비하다고 느껴진다.

입력을 그냥 외부로 전달하는 수준이면 단순 위임 패턴에 지나지 않는다.
입력 해석, 전처리, 정책, 실패 표현의 책임은 개발 환경에 따라 이미 정해져있을 수 있다. 예컨대 Unity 6에서는 입력 전처리 책임의 일부를 Input System에서 해결한다.

어쩌면 InteractUI는 "무조건 dumb해야 한다"기보다는,
입력 장치에 가까운 전처리까지는 담당하고,
도메인 정책은 외부 객체에게 넘기는 식으로 봐야 할 수도 있다.

예를 들면 클릭/드래그 구분, hold 판정, UI 내부 선택 상태 같은 것은 InteractUI가 어느 정도 알아도 될 수 있다.
반면 "지금 이 행동이 게임 규칙상 가능한가"는 여전히 외부 정책 객체가 판단하는 게 맞다.

아직 결론은 확정하지 못했다.

다만 지금 기준으로는 이렇게 정리할 수 있을 것 같다.

```text
UI = View + Interact 관점은 유효하다.

하지만 View와 Interact를 symmetric하게 보긴 힘들다.

View는 데이터와 갱신 이벤트만으로 꽤 잘 닫히지만,
Interact는 입력 해석과 도메인 정책 사이의 경계를 추가로 고민해야 한다.
```
